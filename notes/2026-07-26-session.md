# 2026-07-26 — Phase 3D-1: `Board3D` spike

Todd's direction: proceed as if we're going to fully animated 3D robots
and boards. This phase builds the spike that answers the three questions
that could kill that direction, deleting nothing.

## What was built

| Thing | Where |
|---|---|
| `three` + `@types/three`, reached only via `await import('./scene')` | `package.json` |
| `--export-glb` mode reusing `build(seat)` verbatim | `scripts/blender/robots.py`, `scripts/render-robots.mjs --glb` |
| Four static chassis meshes | `public/models/robot-{0..3}.glb` |
| WebGL renderer with the DOM `Board`'s exact props | `src/components/board3d/` |
| `?render=3d` flag, one line per call site | ProgrammingView, ReplayPlayer, OnlineGameScreen |
| `glb` in the precache glob | `vite.config.ts` |

Untouched: engine, EventLog, Convex, `visualState.ts`, `Board.tsx`,
`Tile.tsx`, `BoardThumb.tsx`, `EditorBoard.tsx`.

`Board3D`'s props are `Parameters<typeof Board>[0]` — derived from the DOM
board rather than copied, so the two cannot drift without a typecheck
failure, and `Board.tsx` still needed no edit.

## Two things the first pass got wrong

1. **Canvas sizing.** Sizing the canvas by board aspect ate the entire
   `100dvh - 12rem` height budget, so the hand and registers fell below
   the fold — the DOM board caps its tiles at 52px and never does that.
   Fixed by sizing off `tileFit()` itself: width = `tile * board.width`,
   height = `tile * (height * sin(elev) + 1.5)`. Tilting costs the board
   depth, so the 3D board needs *less* height than the DOM grid.
2. **FOV 34 was too wide.** On the 17-row composed board the near rank
   rendered twice the size of the far one and the top was unreadable.
   FOV 20 ("orthographic-ish", as planned) keeps tiles roughly uniform
   while still giving the chassis perspective to sit in.

Also replaced: checkpoint/spawn numbers were pips in a row, which read as
a face rather than a number. They're canvas-texture digits now, matching
what the DOM board draws.

## Deliberately absent

3D-4 owns full event parity. Missing: speech bubbles, bump flash,
fall/respawn animation, checkpoint pop. Laser beams and damage flashes
are in so the look comparison is fair. `settled()` never returns true on
a board with conveyors — the belts keep the rAF loop alive by design.

# Phase 3D-2 — Player camera control (same day, after the 3D-1 gate)

Todd's ask, immediately on passing the gate: drag and tilt the view during
both planning and replay, a "lock to my bot's area" toggle, and the ability
to re-watch a turn with different settings. That reordered the roadmap —
board assets are polish, camera *ownership* is architecture — so this landed
as 3D-2 and assets slid to 3D-3.

## The design decision

**Director owns the subject, player owns the viewpoint.** The director keeps
choosing which cell is framed and how close the action wants to be; the
player owns yaw, tilt, and a zoom *multiplier* over the director's distance.
Composing rather than replacing means an orbited angle survives the camera
flying to the next laser hit. Only panning takes the subject off the
director, and that flips follow to `free` so it's a visible state.

Modes: `action` (default) / `robot` (local player, wider radius so pushes and
lasers stay in frame) / `free`. In a **hot-seat replay** there is no local
player, so *My robot* disables itself with a title saying why — by design,
not an oversight.

## Built

- `board3d/viewMath.ts` — pure, `three`-free: clamps (tilt 18–85°, zoom
  0.45–2.2×), spherical placement, board half-extents under yaw+tilt, pan
  vector. 24 new tests, incl. a guard that yaw 0 / tilt 52 / zoom 1
  reproduces 3D-1's exact camera *and* its framing terms.
- `board3d/controls.ts` — hand-rolled Pointer Events. Not OrbitControls: it
  insists on owning distance, which is exactly the half we handed the
  director. One code path for mouse and touch.
- `board3d/camera.ts` — composes. `focus()` and its easing untouched; the
  player's input eases at 0.12 s against the director's 0.36 s so dragging
  feels attached to the finger while fly-ins stay cinematic. `refit()` is
  gone: the pull-back is now re-solved from the live yaw/tilt every step.
- `services/viewSettings.ts` — persisted view + the focus player, following
  audio.ts's precedent. A service, not props, so `BoardProps` stays identical
  and `Board.tsx` needed no edit.
- Overlay (`.board-3d-controls`), **↺ Watch again** in ReplayPlayer,
  `window.__board3d.view()`.

## Two bugs the browser caught that the types could not

1. **Stale focus player.** The overlay read it during render, but the screen
   being replaced clears its seat in effect *cleanup* — which lands between
   the two. A hot-seat replay inherited the last programmer as "me". Fixed by
   re-syncing inside the subscribe effect.
2. **Pinch flipped follow to `free`.** The two pointers report their moves in
   separate events, so mid-frame the two-finger centre is computed from one
   updated and one stale finger and swings half the step each way — a
   spreading pinch racks up travel while going nowhere. The pan deadzone now
   measures *net displacement from where the pinch started*, not accumulated
   travel.

Both are the kind of thing only a real browser finds. Worth remembering for
3D-4/3D-5: anything reading a service during render needs the catch-up sync,
and any multi-touch metric needs to be net, not cumulative.

## Known-correct oddity

`focus()` clamps the subject to keep the framing over the board, so a robot
in the outer ~4.6 tiles never centres. Correct (the focus window is nearly as
wide as these boards) but it makes "subject == robot cell" the wrong
assertion at the rim; `view().subject` documents this.
