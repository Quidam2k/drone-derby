# 2026-07-27 — Phase 3D-3: Blender board tile kit

The 3D board stops being primitives. Every tile piece is modelled in
Blender, shipped as one `tiles.glb`, and instanced by the existing
`Batch`/`InstancedMesh` machinery. Art direction: industrial factory floor,
deliberately not the DOM board's flat panel palette.

| Thing | Where |

Pieces: `floor`, `conveyor`, `chevron`, `gear`, `pit_shaft`, `pit_rim`,

## The three decisions that make it work

**One material, palette in the mesh.** The whole kit is two materials —
`tile_pbr` (a generated tiling wear texture + packed ORM) and `tile_glow`.
Colour rides in per-vertex `COLOR_0`, which glTF multiplies into the base
colour, so a grey deck, a yellow wall and an orange gear share one material
and one texture upload. No atlas, no bake step, no UV packing problem.

The exporter only understands specific node graphs, so the graphs are
exactly the two shapes it recognises: image straight into Base Color, and
one image split into Roughness/Metallic. Nothing in between — the vertex
palette needs no node at all, because glTF's base colour is already
`factor × texture × COLOR_0`.

**Byte, not float, colour attribute.** Both round-trip to identical linear
values through the exporter; `FLOAT_COLOR` costs 16 bytes a vertex against
`BYTE_COLOR`'s 8. Worth 95 KB across the kit — measured, not assumed.

**Local frames match the primitives they replace.** Each piece is modelled
in the same frame as the `BoxGeometry`/`TorusGeometry` it stands in for, so
every placement in `boardMesh.ts` is unchanged and the fallback is a
one-line `??` per piece. The chevron in particular keeps its exact
footprint (points north, lies in XZ, origin-centred, x ±0.30, z 0.10→-0.17)
or the belt scroll in `tick()` stops reading as continuous.

## Measured (production build, `npm run preview`, SW unregistered)

| | 3D-2 | 3D-3 |
|---|---|---|
| Main JS gz | 116.15 KB | **116.15 KB** (unchanged — the loader is in the scene chunk) |
| `scene-*.js` gz | 173.33 KB | **174.10 KB** (+0.77) |
| Precache | 2134.75 KiB / 40 | **2852.96 KiB / 41** (+718.21 KiB) |
| `tiles.glb` | — | **733,164 B = 715.98 KiB** |

Of the .glb, ~99 KB is the two 256² textures (`tile_wear` 57 KB,
`tile_orm` 42 KB); the rest is 11,380 triangles of geometry. Compression
(Draco/meshopt) is still untried and is still the lever if the precache
number has to come down.

**Draw calls**, 4-player Grand Circuit (composed 12×17), counted by
patching the GL prototypes — so this is raw GL draw calls *including the
shadow pass*, a larger number than `renderer.info.render.calls`:

- with the kit: **86/frame**
- with `tiles.glb` renamed away (same code, all primitives): **88/frame**

No regression, a 2-call drop. The board contributes 14 instanced batches
either way: the kit retires the gear-teeth batch (one toothed mesh now)
and spends it on splitting the tile deck into floor and belt, which the
belt needs anyway because a modelled belt bed has to face the way it runs.

**Frame time**, same board, replay running, busy-loop calibrated:

| | calibration | median | p95 | worst | >20 ms | fps |
|---|---|---|---|---|---|---|
| unthrottled | 17.4 ms | 16.7 | 16.8 | 16.8 | 0/240 | **60.0** |
| throttled | 163.2 ms (**9.38×**) | 16.7 | 33.3 | 33.5 | 25/240 | **54.3** |

The calibration is not decoration: the first run reported a 0.98× factor
and identical throttled/unthrottled frame stats, which looked like the
throttle silently failing. It was a cold-JIT baseline — the busy loop's
first execution ran 10× slow. Warm it first or the ratio is meaningless.

**Zero console errors and warnings** across hot-seat, replay and unmount.
Canvas count goes to 0 on unmount.

**Kit-missing path**: `tiles.glb` renamed → board builds entirely from
primitives, exactly one warning (`[board3d] tile kit failed to load —
falling back to primitives`), no crash, no visual gaps. This is the
3D-1/3D-2 look, intact as the low-end path.

**Flag isolation** still holds: lobby, hot-seat setup and `#/editor` fetch
neither `scene-*.js` nor any `.glb`.

## Two traps worth remembering

1. **`page.goto` to a URL differing only in the hash does not reload.**
   The first hour of look-iteration was spent judging a page that had
   loaded the very first export and never reloaded — new `.glb`, new JS,
   new `localStorage` all ignored. `fetch(url)` reported the fresh bytes
   while the loader still held the stale ones, which made it look like a
   caching bug. `location.reload()` is the fix; a magenta-deck test is what
   proved it (the board stayed grey, so the asset in play wasn't the asset
   on disk).
2. **Metalness ran the look, not albedo.** The first pass had the deck at
   metal 0.78 and the environment simply took the surface over — a
   near-white board with every functional piece washed out. Metal is a
   painted-deck 0.40 now, env intensity 0.85 → 0.6, and the deck albedo is
   dark on purpose: it is the background the whole board reads against.

## Lighting

Rebalanced for metal, which has no diffuse response — the environment, not
the lamps, is what a deck plate shows you. `environmentIntensity` 0.3 →
0.6, hemisphere 0.55 → 0.40, key 2.4 (unchanged; it is also doing the
specular streaks and every shadow), rim 0.9 → 0.75, exposure 1.05 → 1.0.

## Side note: the robots.py refactor is faithful

`robots.py` now imports its primitives from `common.py`. Re-exporting the
four chassis to a scratch dir gives byte-identical files for seats 0, 2, 3.
Seat 1 differs by 1–2 vertices out of 12,242 — but so does re-running the
*pre-refactor* script, which produced a third value again. Triangle counts
are identical across all three; it is the exporter's vertex dedup jittering
on float equality, and it predates this phase. `public/models/robot-*.glb`
was not regenerated.
